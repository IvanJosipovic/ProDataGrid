# Flat-layout benchmark results — 2026-08-12

This run compares the nested compatibility layout with the revised flat sibling
surface on the same 149,792-node hierarchy, 1200 × 760 headless host, 520-pixel
DataGrid viewport, and six cell paths. Both layouts realize 15 rows and 90 cells
with 32-pixel content plus the same 1-pixel horizontal grid line.

Environment: BenchmarkDotNet 0.15.8, Release, tiered compilation disabled,
macOS 26.6 (Darwin 25.6.0), Apple M3 Pro, .NET SDK 10.0.201, .NET 10.0.5
Arm64 RyuJIT, concurrent workstation GC. Every comparison used three launches,
three warmups, ten measured iterations, one invocation, and one unroll.

`Ratio` is flat time divided by nested time. `Allocated` is managed allocation
traffic per operation, not retained heap, RSS, native, or GPU memory.

## Architecture changes validated by this run

- Flat row geometry now matches nested geometry and draws the horizontal grid
  line directly without adding another visual.
- Fixed-height, non-auto drawn cells no longer invalidate measure when only
  their content changes.
- Visible-column geometry is computed once per presenter layout pass.
- The flat presenter owns one shared drawn-text layout cache, so recycled cells
  can reuse shaping results across rows and expand/collapse cycles.
- Flat-cell suppression is deferred until synchronization, avoiding hide/show
  churn for cells immediately reused by another realized row.

## Pending layout after collapse

Iteration setup expands and lays out the hierarchy, dispatches `CollapseAll`,
and leaves layout pending. The benchmark measures completion of that pending
Avalonia layout and render work.

| Cell path | Nested | Flat | Ratio | Speedup | Nested allocated | Flat allocated | Allocation change |
|---|---:|---:|---:|---:|---:|---:|---:|
| Standard retained | 3.598 ms | 3.385 ms | 0.94 | 6% | 1117.53 KB | 1108.44 KB | -1% |
| Optimized retained theme | 3.021 ms | 2.936 ms | 0.97 | 3% | 1101.38 KB | 1094.15 KB | -1% |
| Optimized hierarchy presenter | 2.828 ms | 2.710 ms | 0.96 | 4% | 1060.76 KB | 1053.53 KB | -1% |
| Direct retained hierarchy | 2.824 ms | 2.731 ms | 0.97 | 3% | 1060.76 KB | 1053.48 KB | -1% |
| Direct hierarchy + built-in drawn | 4.085 ms | 2.702 ms | 0.66 | **34%** | 1747.91 KB | 1024.09 KB | **-41%** |
| Direct hierarchy + custom Skia | 1.181 ms | 1.170 ms | 0.99 | 1% / parity | 331.28 KB | 329.33 KB | -1% |

The built-in drawn path is the major layout win: 1.51× throughput with 41%
less managed allocation. Retained paths improve modestly because their control
content remains the dominant cost; flattening removes one presenter per row,
not the retained cell subtree. The custom Skia path was already using a shared
column cache, so centralizing cache ownership does not materially change it.

operation includes `CollapseAll`, dispatcher work, layout, and headless render
completion.

## Original hierarchy-model benchmark comparison

The original model-only suite was rerun with the exact same 3 × 10
configuration. Flat visual layout is not involved in these operations. Managed
allocations are identical in every case, confirming that the visual
architecture did not regress the earlier hierarchy optimizations.

| Benchmark | Previous | Current | Previous/current allocated |
|---|---:|---:|---:|
| `CollapseAll`, 149,792 nodes | 4.184 ms (median 3.943) | 3.239 ms (median 3.254) | 4.39 / 4.39 KB |
| `ExpandAll`, wide 2,555 | 121.46 μs | 122.43 μs | 369.66 / 369.66 KB |
| `ExpandAll`, binary 4,094 | 350.15 μs | 358.72 μs | 705.59 / 705.59 KB |
| `ExpandAll`, depth-128 512 | 81.21 μs | 80.55 μs | 123.46 / 123.46 KB |
| async wide, batched | 201.4 μs | 203.1 μs | 402.25 / 402.25 KB |
| async binary, batched | 703.7 μs | 704.1 μs | 1812.12 / 1812.12 KB |
| async deep, batched | 133.5 μs | 135.3 μs | 392.76 / 392.76 KB |

The scaling lane remains linear: 51.49, 93.49, 178.76, 353.76, 714.83, and
1460.44 μs for 510 through 16,382 binary-tree nodes. The separate 50,000-depth
stack-safety process passed. The lower current `CollapseAll` mean should be
treated as reduced run noise, not as a flat-layout optimization; no hierarchy
model code changed in this architecture pass.
